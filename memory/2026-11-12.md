## 现象定性（用户观察 ↔ 代码，已全部对上）
- **iOS 其实完整起到用户空间**：`exec SpringBoard` / `lockdownd` / `backboardd` / `chronod` 都在跑，
  FB swap 最多 16 次，无 panic、无 watchdog 重启。「进不了锁屏」不是启动卡住，是 **UI 内容没被渲染**。
- **紫块 + 白条** = `xnu/iokit/Kernel/arm/SweetFramebuffer.cpp` 的 `AppleCLCD::present()` 里
  **0144 liveness marker**：`row[x]=0xffff00ff` 画左上 96×96 紫方块，`0xffffffff` 画全宽 12px 白条，
  `by=(bar++ % 32)*72` 每次 present 下移 72px。源码注释原文：
  *"if the panel shows them, the DPU still scans fPixels and what the screen lacks is content, not the display path."*
  白条「很慢」是因为 present 由 vsync timer + `fDirty` 驱动，本轮 swap 只有个位数。
- **橙 / 白 / 蓝三色带** = `gauguin_gpu.c:2728` 的 boot selftest（`step22 px ... 0xff0080ff`、
  `panel rows orange=32 blue=32`），用 2D 管线直接画。v135 因为更早就挂、连 liveness marker 都没走到，
  所以画面退回三色带。
- **亮 → 暗 → 再亮** = `SWEET FB: display on(7831) → off(17863) → on(21800)`，backboardd
  `kSweetFBRequestPowerChange` 触发；v130 为 7842/18553/21777，逐帧一致，与软件合成路径时序相同。
- **滚动日志 + 触摸坐标** = 内核 console 与 `SweetHID.cpp:534 "SWEET HID: touch %d ... at %d,%d"` 仍工作。
  即 **CPU 写屏 / DPU scanout / swap / 电源时序 / 触摸输入全好，缺的只是 GPU 合成的 UI 内容**。

## 纠正此前误判（不要再走回头路）
1. **`CP_HW_FAULT=0x40000` / `gauguinclr=4` 是 RED HERRING**。boot 自检成功（`panel RETIRED`）时
   就常驻 `fault=0x40000 int=0x4 cb1 fsr=0x400`；clr=1/2/3/4 全部无效。`memory/2026-11-11.md`
   的核心结论作废，0179–0183 一直在清错东西。
2. **0178「顶层 IB 尾部漏扫」前提错误**：v125 与 v124 完全同构（仅 GEM 地址 -0x8000），
   `0175 san ... dwords=241` / `walk hung end 241/241` 证明顶层 IB 已完整解析，
   其中根本没有 0x3f/0x37/0x63 —— NOP 命令流路线从这里就该收手。
3. **0183 的 SMMU 路由假设被证伪**：`s2cr2=0x301` 正好等于 `S2CR_TRANS_CB1`((3<<8)|1)，
   `smr2=0x80000000` = `SMR_VALID|SID0`，`0183 route drifted` 8 次 recover 里一次都没打印。
4. **SMMU 映射 / cache flush 链路是完整的**：`SURFACE_BO id=2 handle=149 iova=0x51252000`、
   `id=3 handle=165 iova=0x52bca000`（1125x2436 bpr=4544），提交 `bos[]` 里确实带 handle=165；
   `map_bo_pages()` → `gauguin_gem_map()` 每页写 `PTE_PAGE_NC` 并 `gauguin_gem_tlb_flush()`；
   GEM VA `0x50000000..0x6fffffff` / 256 张 L3 表，最大 iova `0x54512000` 在范围内；
   boot `GEM selftest PASS`（`memwrite=0x600dbeef`）。
5. **「GPU 从头到尾没写 IOSurface」也要修正**：`scratch2=0x6000088` 证明前 136 个提交
   （`attachment_clear_frag_lph`，`nr_bos=6 words=68`）fence 真的被 GPU 写了，`trace submit cp done`
   不是假阳性；`src px 全 0` 是 **清屏成功** 的结果。第 137 个提交（`nr_bos=22`、IB `0x5041e000/241`、
   引用 surface 3 `0x52bca000`）才是第一个带 UI 的 draw，它卡死。
6. **recover 的 `RETIRED` 是假阳性**：`rptr=0` 是 scratch WAI 影子值，`reg=0xc/0x11` 只是硬件 RPTR
   推进（只取包没执行）。0183 起改标 `FETCHED_ONLY`。boot 对照 `rptr=12/17`、
   `memwrite=0x600dc0de flush=0x600df1a5 status1=0x1000000`；recover 后 `memwrite=0`、
   `status1=0x81004106`。
7. **按键教反了**：**电源 + 音量上 = OrangeFox recovery**，电源 + 音量下 = **fastboot**。
   `fastboot reboot recovery` 可把 fastboot 转回 recovery（实测有效）。误进 fastboot 属强制断电，
   SWEETLOG header 会被清零。

## 最新方案（v136，尚未实施）
1. **保留 sanitize**（`gauguinsan` 默认开）。前面四版是在「已被改写过的命令流」上继续补 NOP，
   而 v135 证明 sanitize 一直在绕过这个 amble，才让系统跑到第 139 个提交。
2. 针对 stamp 定位到的 **`CP_INDIRECT_BUFFER_PFE → 0x5041b600 / 196 dwords`** 这条 nested amble：
   - A：在 `gg_ib_sanitize()` 里对匹配该目标的 PFE 入口做**长度保持 NOP**（`gg_pkt7(CP_NOP, plen)`
     + payload 清零），或直接把目标 196-dword IB 整体 NOP；
   - B：或把该 amble 内的 AHB / 特权寄存器写按 deny-list 全部清干净（0172 只改了 18 处，
     hang dump 里仍有残留 type-4 写）。
3. **与既有实验的区别（关键）**：v133 的 `gauguinamb=2` NOP 的是**顶层 `CP_SET_AMBLE`(op 0x55)
   → `0x5041e600/207`**，不是这条 0x3f nested 入口，所以从来没覆盖到；0184/0185 同理只处理
   plen<3 短包与 WFI。v136 是第一次打在 stamp 指出的确切位置。
4. 判据：`src px / panel px` 非 0 > 一切；辅助看 `mark` stamp 是否推进过 packet 11、
   HUNG 是否从第 139 个提交继续后移、`-60` / `no ring space` 是否下降。
5. 若 v136 仍全 0 → **彻底放弃命令流**，转 SQE 微码 PC / 真正的 GX 硬件复位。
   依据：zap 只重置 secure firmware，清不掉 ROQ 残留与 `status1`；boot 注释
   `AUTH_AND_RESET puts the core back in the secure domain, so the ROQ silently drops all non-secure
   packets`，v41/0115 已证「zap 跑在 SQE_CNTL/ME_INIT 之后 → CP consumed every later packet but

## v136 实测结论（19:10，最新）：wedge 不在命令流，在**环形缓冲区回绕**

- 日志 `out\sweetlog-v136\v136.txt`（22,021 行，flush #0），镜像
  `out\v136\shim\out\shim-boot.img`，17,678,336 B，sha256
  `0556e575479de561bf9da1d6c6218588f74d28434df34021da7accac81ab781b`。
- **0187 本身工作正常**：`impl 0187`、`0187 san=320`、`mark count=313`、
  `mark skip=1`；第 3 个提交（第一个 22-IB UI draw，`241->671`）**成功退休**
  （`submit state OK fence=0x6000003`）。对“注解副本”做 sanitize 是对的，不是病根。
- **第一次失败是提交 #137**（`fence=0x6000089`）：`HUNG rbbm=0xc01005
  status1=0x81004106`、`STUCK (rptr=4112 wptr=4112)`、`ib1=0x40101000/0 rem=0`、
  `mark ib0 last=0 next=0`（stamp 从未写入）、`fault=0x40000`（良性）。
  从 `0x89` 到 `0x13a` 共 178 个提交全失败；8 次 recover 全假（`memwrite=0`，
  `ME_INIT`/`SET_SECURE_MODE` 一直 `FETCHED_ONLY`）。
- **原因是 ring 回绕（观测 + 算术，不是猜测）**：`ring_dw = CPMEM_RING/4 = 4096`
  dwords（`RB_CNTL_VAL 0x0800020c` → BUFSZ=12 → 4096 dwords）。step22 在 wptr=142
  退休，boot 自检把它推到 1783，136 次提交 × (4×1+13)=17 = 2312 → **4095**。
  第 137 个提交从最后一个 slot 开始、长 17 dwords，包体按 `wp % ring_dw` 落在 0..15，
  但寄存器被写成未取模的 **4112**。CP 照抄（`rptr=wptr=4112`），去取 ring 窗口
  尾部全 0 区域，一个 IB 都没执行（`rem=0`、无 stamp、无 fence），之后 8 次 recover
  都没救回来。恢复后 ring 归零、驱动从 0 重新累计到 2928（约 170×17），
  反过来证明 4112 是累计结果，不是野写。
- **这也解释了“换命令流没用”**：v131/v132/v133/v136 改的是四种不同命令流，
  第一次 HUNG 的硬件快照却一致；真正的触发点是“第 137 个提交跨过 ring 末尾”。

## v137 实测结论（19:20，最新）：ring 是 **8192 dwords**，4096 是把块内偏移当成了大小

- 日志 `out\sweetlog-v137\v137.txt`（40,442 行，flush #44），镜像
  `out\v137\boot.img`，17,678,336 B，sha256
  `fcb7a02c926b15f47289d47158036d2a290db9ee2c0cf321d8095a3d98e9c04b`。
- 0188 的掩码按设计触发了，回绕也仍发生在提交 #137，但 **wedge 没有移动**：
  `STUCK (rptr=4272 wptr=16)` —— 注意 **rptr=4272 > 4096**。CP 没有在 4095
  回绕，而是继续线性取指，读到从未写过的 ring 后半段（slot 4096 以后），
  一个 IB 都没执行（`mark ib0 last=0`）就死了。
- 之后全是死的 ME：57 次 `STUCK`、3 次 `HUNG`、677 次 `submit failed: -60`、
  0 次 `no ring space`、0 次 panic；13 个 `src px` 采样全为 `0x00000000`，
  14 个 `panel px` 全为 0（手机显示仍是紫屏+白条）。
- **结论**：CP ring 是 **8192 dwords（32 KiB）**，`ring_dw = CPMEM_RING / 4u`
  = 4096 就是 bug —— 把 CP 块内偏移 `0x4000` 当成了大小。三重佐证：
  窗口是 `CPMEM_RING 0x4000 .. CPMEM_SQE 0xc000` = 32 KiB = 8192 dwords
  （0182 的恢复代码本来就在 scrub 8192 dwords）；L3 给 `CP_VA_RING` 映射了 8 页；
  `RB_CNTL_VAL 0x0800020c` 的 BUFSZ=12 = log2(32 KiB / 8 B)。前 136 个提交
  能过，只是因为那时还没人写到 dword 4096。
